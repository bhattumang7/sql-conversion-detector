SilentScan rules

234 rules. 141 carry fix guidance; 18 link a real fixture. Generated from the same catalog SARIF's own rules block reads — never hand-edited.

silentscan/call-graph/argument-type-mismatch

A real EXEC call site passes a caller-side variable whose declared type risks silent data loss against the callee's own declared parameter type - an assignment-shaped conversion at parameter marshalling, not a predicate, classified the same way an INSERT/UPDATE assignment's silent data loss is.

silentscan/catalog/cascading-foreign-key

A foreign key with a non-NO_ACTION ON DELETE/ON UPDATE action - a single DML statement against the referenced table silently cascades to every dependent row in the child table too, with no visible predicate change at the call site.

silentscan/catalog/check-constraint-null-not-handled

A nullable column's own CHECK constraint predicate has no IS NULL/IS NOT NULL test against that column anywhere in the predicate - SQL Server's three-valued logic means a comparison against NULL evaluates to UNKNOWN, never FALSE, and a CHECK constraint only rejects a row when its predicate is FALSE, so a NULL value silently passes a constraint that reads as if it forbids bad data.

Fix
Add an explicit IS NULL/IS NOT NULL test for the column in the CHECK constraint predicate, so a NULL value isn't silently accepted through three-valued logic.

silentscan/catalog/check-constraint-on-identity-column

A CHECK constraint's own definition directly references an IDENTITY column - the identity counter advances even through a failed insert, so a numeric-threshold CHECK here rejects every insert deterministically until the counter happens to satisfy it, then silently stops mattering forever with no code change.

Fix
Do not enforce a numeric-threshold CHECK directly on an IDENTITY column - the counter advances even on failed inserts, so the constraint stops meaningfully applying once it happens to be satisfied.

silentscan/catalog/column-collation-drift

A string-family column's own collation differs from the database's default collation (or, for a temp table/table variable, from tempdb's effective collation) - a conversion seed: any future comparison against a column/literal carrying the baseline collation risks a collation-conflict compile error or a forced-scan implicit conversion. Catalog-only, detected before any query reaches the column.

silentscan/catalog/cross-table-fk-type-drift

A foreign-key column pair's declared types and/or collations genuinely differ - a conversion seed on every JOIN that follows this relationship, detected from the catalog alone (sys.foreign_key_columns), independent of whether any scanned query actually joins on it.

silentscan/catalog/default-constraint-on-nullable-column

A column carries a DEFAULT constraint but is still nullable - a DEFAULT only ever applies when the column is OMITTED from an INSERT's own column list; any caller that supplies NULL explicitly (a common ORM-generated full-column INSERT shape) bypasses the default entirely, silently, with no error.

Fix
Make the column NOT NULL, or otherwise stop relying on the DEFAULT for callers that supply NULL explicitly - a DEFAULT only applies when the column is omitted from the INSERT's own column list.

silentscan/catalog/max-typed-column

A string/binary column is declared MAX-typed - it can never be an index key column at all, so any predicate/join on it can never seek regardless of how it's used. Catalog-only structural fact.

silentscan/catalog/non-persisted-computed-column

A computed column with is_persisted = 0 (sys.computed_columns) - its definition is recomputed from the base row on every read that touches it, independent of whether that definition calls a UDF at all. Catalog-only structural fact, never fires on a PERSISTED computed column regardless of whether it's also indexed.

Fix
Mark the computed column PERSISTED so its definition isn't recomputed from the base row on every read that touches it.

silentscan/catalog/rls-predicate-unindexed-column

An enabled Row-Level Security FILTER predicate's own bound column(s) lead no active index on the secured table - the predicate is silently applied to every SELECT/UPDATE/DELETE against this table (not just queries whose own WHERE clause happens to filter the same way), so the engine cannot seek and must evaluate it as a residual, per-row filter over a full scan on every access. Oracle-confirmed scan-vs-seek contrast; the checklist's own 'forces single-threaded execution' claim was not reproduced live on this tool's own standing engine build and is deliberately not asserted here.

Fix
Add an index (or extend an existing one) covering the Row-Level Security FILTER predicate's own bound column(s), so it can be seek-evaluated instead of scanned on every access.

silentscan/catalog/stale-select-star-view

A view's own outermost SELECT * over a single base table has a compiled column list (frozen at CREATE/ALTER/sp_refreshview time) that no longer matches that base table's current column list - a later ALTER TABLE ADD/DROP COLUMN never propagates to the view. Confirmed to silently surface real data under a stale, wrong column label when a drop and a later add shift column identity, not merely a missing/extra column.

silentscan/catalog/temporal-history-index-gap

A system-versioned temporal table's CURRENT side carries a nonclustered index with no structurally matching index (same key columns, same order) on its HISTORY side - oracle-confirmed that FOR SYSTEM_TIME AS OF/BETWEEN rewrites to a UNION ALL of the two tables, so a predicate that seeks the current-table branch via this index degrades to a full scan of the history-table branch. PRIMARY KEY/UNIQUE-constraint indexes are never compared - the engine itself forbids either constraint on a temporal history table.

Fix
Create a structurally matching nonclustered index (same key columns, same order) on the HISTORY table to mirror the one on the CURRENT table.

silentscan/catalog/tvf-return-database-collation

A non-schema-bound table-valued function's own RETURNS @t TABLE(...) declares a character-typed column with no explicit COLLATE clause, so its collation was implicitly resolved against the CURRENT database's default collation at CREATE/ALTER time and baked in (sys.sql_modules.uses_database_collation) - a later ALTER DATABASE ... COLLATE silently leaves the function's already-compiled return shape disagreeing with the database's new default. Schema-bound modules are excluded from this finding: oracle-confirmed that schema-binding sets this flag unconditionally regardless of whether the module touches string data at all, so it carries no differentiating signal there.

Fix
Add an explicit COLLATE clause to the table-valued function's own RETURNS TABLE column declaration instead of relying on the database's default collation at CREATE/ALTER time.

silentscan/catalog/untrusted-check-constraint

A CHECK constraint the engine itself does not trust (sys.check_constraints.is_not_trusted) - almost always the result of a WITH NOCHECK re-enabling ALTER TABLE statement. The constraint may not actually hold over existing rows, and the optimizer forfeits constraint-based rewrites that assume it does.

silentscan/catalog/untrusted-foreign-key

A foreign key the engine itself does not trust (sys.foreign_keys.is_not_trusted) - almost always the result of a WITH NOCHECK re-enabling ALTER TABLE statement. Forfeits join-elimination and other constraint-based query rewrites for every query that touches it.

silentscan/catalog/with-recompile

The module was authored WITH RECOMPILE (sys.sql_modules.is_recompiled) - every execution compiles a fresh plan and discards it immediately rather than caching it, so the module's own cost never accumulates in the plan cache at all, invisible to any monitoring that reads sys.dm_exec_cached_plans/sys.dm_exec_query_stats.

silentscan/control-flow/case-expression-missing-else

A simple CASE expression has no ELSE - an input value matching none of the WHEN values silently evaluates to NULL, no error raised.

Fix
Add an explicit ELSE branch to the CASE expression.

silentscan/control-flow/cursor-fetch-column-count-mismatch

A cursor FETCH INTO variable count doesn't match its own cursor's defining SELECT column count - always fails at runtime.

Fix
Match the FETCH INTO variable list's count to the cursor's own defining SELECT column count.

silentscan/control-flow/dirty-read-isolation-hint

NOLOCK/READUNCOMMITTED allows dirty reads and can miss or double-count rows during a concurrent page split.

Fix
Avoid NOLOCK/READUNCOMMITTED where dirty reads or missed/double-counted rows during a concurrent page split are not acceptable.

silentscan/control-flow/empty-catch-block

A CATCH block has no statements - every error reaching it is silently swallowed.

Fix
Add real error handling (at minimum a THROW or logging) inside the CATCH block instead of leaving it empty.

silentscan/control-flow/goto-usage

A GOTO statement - unrestricted jumps make control flow harder to follow, and this tool's own dead-code analysis declines entirely for a routine that contains one.

Fix
Restructure the control flow to avoid GOTO - unrestricted jumps also disable this tool's own dead-code analysis for the routine.

silentscan/control-flow/legacy-identity-intrinsic

@@IDENTITY returns the last identity value inserted in this session across any table/scope - prefer SCOPE_IDENTITY().

Fix
Use SCOPE_IDENTITY() instead of @@IDENTITY.

silentscan/control-flow/non-deterministic-case-input

A non-deterministic function (NEWID/RAND/CRYPT_GEN_RANDOM) is used as a simple CASE expression's input - oracle-confirmed to be re-evaluated separately per WHEN comparison, not once, making every WHEN branch effectively unreachable.

Fix
Assign the non-deterministic function's result to a variable first, then use the variable as the CASE input, instead of calling the function directly as the CASE input.

silentscan/control-flow/trigger-emits-output

A trigger emits a result set or message back to whatever connection fired the DML, not the calling application.

Fix
Remove the result set or message the trigger emits - it reaches whatever connection fired the DML, not the calling application.

silentscan/control-flow/truncate-swallowed-by-catch

TRUNCATE TABLE sits inside a TRY block whose CATCH block never THROWs/RAISERRORs anywhere in its own statement tree - oracle-confirmed a real TRUNCATE failure (e.g. an enforced FK reference, Msg 4712) is silently swallowed here, with execution continuing as if the TRUNCATE had succeeded and no error reaching the caller. TRY with no matching CATCH at all is a hard parse error (Msg 102) and can never occur in valid T-SQL, correcting this item's own original framing.

Fix
Add a THROW or RAISERROR inside the CATCH block so a real TRUNCATE failure doesn't get silently swallowed.

silentscan/control-flow/unassigned-output-parameter

A procedure's own OUTPUT parameter is not assigned on some statically reachable path (a RETURN, or the natural end of the body) - oracle-confirmed a caller's own variable is left completely unchanged by the call on that path (not reset to NULL), so a reused caller variable can silently carry stale data from a previous, unrelated call.

Fix
Assign the OUTPUT parameter on every statically reachable path, including RETURN and the natural end of the body.

silentscan/control-flow/unresolved-transaction

A BEGIN TRANSACTION reaches a RETURN/THROW, or the natural end of the module body, on some statically reachable path with no intervening COMMIT/ROLLBACK - oracle-confirmed directly: SQL Server itself raises Msg 266 ("Transaction count after EXECUTE indicates a mismatching number of BEGIN and COMMIT statements") and leaves the calling session's @@TRANCOUNT elevated by one the instant such a procedure returns, holding that transaction's locks indefinitely.

Fix
Ensure every RETURN/THROW path, and the natural end of the module body, is preceded by a matching COMMIT or ROLLBACK for every BEGIN TRANSACTION.

silentscan/control-flow/waitfor

WAITFOR DELAY/WAITFOR TIME holds the calling worker thread idle for the full delay/until-time - a documented, unconditional cost contributing to worker-pool exhaustion under load, and (inside an open transaction) extended lock hold duration.

silentscan/correctness/between-end-of-period-boundary

A BETWEEN predicate's upper bound literal has fewer fractional-second digits than the TIME/DATETIME2/DATETIMEOFFSET column's own declared precision - a correctness bug, not a sargability one: rows in the precision gap are silently excluded, oracle-confirmed. Rewrite as >= start AND < (start of the next period) instead.

Fix
Rewrite the BETWEEN predicate as >= start AND < (start of the next period) instead, so no value in the precision gap is silently excluded.

silentscan/correctness/nonunique-update-source

UPDATE ... FROM ... JOIN where the joined source's own join columns carry no unique index/constraint - if a target row matches more than one source row, SQL Server silently picks a value from an unspecified one of them (plan-dependent, not guaranteed stable across executions). MERGE raises a hard error in this exact situation instead of picking silently. Never fires when the source's join columns are covered by a genuine unique index/constraint, or when the SET clause never reads from the non-unique source.

Fix
Add a unique index/constraint covering the source's join columns, or switch to MERGE, which raises a hard error instead of silently picking an unspecified row.

silentscan/correctness/not-in-nullable-subquery

WHERE x NOT IN (SELECT y FROM t) where y is a nullable column - a three-valued-logic correctness trap. The instant the subquery produces one NULL row, the whole NOT IN evaluates to UNKNOWN for every outer row, so the query silently returns zero rows instead of the expected anti-join result. Never fires when the subquery column is NOT NULL, or when the subquery already filters it with an unconditional WHERE y IS NOT NULL.

Fix
Add a WHERE y IS NOT NULL filter to the subquery (or rewrite the NOT IN as a NOT EXISTS), so a NULL row can't collapse the whole predicate to UNKNOWN.

silentscan/cross-module/inconsistent-lock-order

Two top-level procedures' own direct explicit-transaction write orders disagree on the relative lock order of the same two base tables - the textbook cross-session deadlock shape.

Fix
Make both procedures acquire locks on the two tables in the same relative order.

silentscan/database/auto-close-on

AUTO_CLOSE is ON - the database's connection/buffer-pool state is torn down after the last connection closes and rebuilt from scratch on the next one.

Fix
Turn AUTO_CLOSE OFF.

silentscan/database/auto-create-statistics-off

AUTO_CREATE_STATISTICS is OFF - the optimizer can no longer create a missing single-column statistics object on demand, so a predicate against an unstatted column compiles against a guessed cardinality instead of a real histogram.

Fix
Turn AUTO_CREATE_STATISTICS ON so the optimizer can create a missing single-column statistics object on demand.

silentscan/database/auto-shrink-on

AUTO_SHRINK is ON - a well-known, severe anti-pattern: constant fragmentation churn as the engine shrinks the file and the workload immediately re-grows it.

Fix
Turn AUTO_SHRINK OFF.

silentscan/database/auto-update-statistics-off

AUTO_UPDATE_STATISTICS is OFF - statistics never refresh as the underlying data changes, so every plan compiled against them drifts further from reality the longer the database runs.

Fix
Turn AUTO_UPDATE_STATISTICS ON so statistics keep refreshing as the underlying data changes.

silentscan/database/compatibility-level-behind-engine-default

The database's compatibility level is behind the connected engine instance's own current default (read live from the model system database, not a hardcoded version-number mapping) - it is silently kept on an older cardinality estimator and query-optimizer behavior nobody chose on purpose.

Raise the database's compatibility level to the connected engine instance's own current default.

silentscan/dynamic-sql/analyzed

silentscan/dynamic-sql/concatenated-value-in-constant-sql

Fix
Use sp_executesql with its own @params mechanism instead of EXEC(string)/EXEC(@sql) string concatenation, so one cached plan is reused across every distinct value.

silentscan/dynamic-sql/insert-exec-temp-table-column-count-mismatch

Match #temp's declared column types to the executed procedure's real result-set column types at each position.

silentscan/forced-serial/fast-forward-cursor

A cursor declared FAST_FORWARD (or the equivalent bare FORWARD_ONLY READ_ONLY without an explicit STATIC/KEYSET/DYNAMIC) forces the cursor's own defining query plan serial, confirmed as NonParallelPlanReason="NoParallelFastForwardCursor". This is the opposite of the common 'always use LOCAL FAST_FORWARD' fetch-overhead advice - that advice is still correct for row-by-row fetch cost, but it is specifically what defeats a parallel plan for the cursor's defining SELECT.

silentscan/forced-serial/nonparallelizable-intrinsic

One of a finite, oracle-confirmed list of intrinsic functions/globals (OBJECT_ID, IDENT_CURRENT, ERROR_NUMBER, ERROR_MESSAGE, ERROR_LINE, ERROR_SEVERITY, ERROR_STATE, ERROR_PROCEDURE, @@TRANCOUNT) referenced inside a query with a real FROM clause forces that query's plan serial, confirmed as NonParallelPlanReason="NonParallelizableIntrinsicFunction".

silentscan/forced-serial/table-variable-modification

A read-only reference to the same table variable is unaffected.

A predicate of the shape (Col = @p OR @p IS NULL) - the 'catch-all'/'kitchen-sink' optional-filter idiom.
