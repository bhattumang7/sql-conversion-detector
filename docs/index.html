The loop

Caught on your machine, not in production.

Every rule is provable from the code and the schema, which is what lets the scan run before the commit instead of after the incident. That matters most for SQL nobody read closely — the kind an assistant drafts in seconds and a reviewer skims because it looks fine.

Coverage

Eleven families. One finding schema.

Some rules are oracle-backed and carry a verdict about what the plan will do. Some are pure catalog facts. Some are syntax-only and cheap. All of them read the same code and schema, report the same way, filter the same way, and gate CI the same way.

Conversions & silent write loss

Direction- and collation-aware conversion detection — column side vs. value side, inherited through views and dynamic SQL — plus DML that truncates or rounds your data with no engine error at all.

Sargability & index shape

Function-wrapped columns, leading-wildcard LIKE, column arithmetic, and composite-index predicates that constrain a trailing key while leaving the leading one wide open.

Lineage metrics

The numbers that need the lineage pass to exist at all: real join width after every view and function expands, nested-view depth, CTEs re-run once per reference.

Catalog & database config

Untrusted foreign keys and CHECK constraints, cascading deletes, collation drift, temporal history tables missing the current table's indexes, and database options that quietly cost you.

Plan shape & correctness

Multi-statement functions used as row-count fences, scalar UDFs that block inlining, forced-serial constructs, and predicates that defeat cached-plan cardinality sniffing.

Control flow & transactions

BEGIN TRANSACTION with no guaranteed commit path, a TRUNCATE whose failure a CATCH swallows, an OUTPUT parameter left unassigned on some return path.

Dynamic SQL

Text that can be proven constant is analyzed exactly like static SQL, remapped to its real source line. Anything unprovable is counted and reported, never quietly treated as clean.

Index & physical design

Unindexed foreign keys, duplicate and prefix-subsumed indexes, clustering-key quality, and identity ranges heading for exhaustion — the catalog half of a DBA review.

Query anti-patterns

Row-by-row DML, cursors without LOCAL, MERGE without HOLDLOCK, recursive CTEs with no MAXRECURSION, DISTINCT masking a join fan-out.

Triggers & cross-module

Triggers that collapse a multi-row inserted set into one scalar, triggers re-entering their own table, and write ordering across two procedures that only lineage can see.

Code quality & security

Structural metrics, dataflow-based dead code, duplication, naming, deprecated syntax, hard-coded credentials and weak hash algorithms — same finding schema as everything above.

Precision

A finding you can trust is worth ten you have to check.

Precision beats recall everywhere in this tool. One false positive costs more attention than ten missed true positives, so a rule that can't prove its claim says so instead of guessing.

Proven in the lab, not at scan time

Your scan never asks the server for a plan. But before a verdict-bearing rule ships, it has to earn its claim: it defines a specific plan-XML marker and is checked against a live SQL Server instance rather than a published compatibility matrix. A conversion rule ships only once the plan shows CONVERT_IMPLICIT on the column side — never inferred from whether a small table happened to scan anyway.

Rules state their engine-version sensitivity too: 2017 interleaved execution, 2019 UDF inlining, 2022 cardinality-estimator behavior. Rules that state a purely structural fact need no oracle and claim none. What you get back is what your code makes possible for the engine — a static verdict, never a guess about your workload.

Lineage all the way down

Most analyzers stop at whichever layer they parse first. A dynamic-SQL string proven constant at compile time is reparsed and handed back to the same lineage resolver static SQL uses — so a predicate buried inside EXEC(@sql), against a view built on another view, still traces to the real base column — all of it from the text and the catalog, with nothing executed.

Built for the AI development loop

Written for a machine to read, and to stay put.

Nothing about SilentScan is AI-specific, and that is exactly what makes it usable by an assistant: it is a command-line tool whose entire output is machine-readable, running where the code is being written.

  • ●Machine-readable by default. Versioned JSON or SARIF, deterministically ordered, every finding carrying its rule id, location, resolved base column, indexed flag, confidence tier and the evidence behind the verdict. Enough for an assistant to fix the SQL and re-run the scan to prove the finding is gone.
  • ●It stays on your machine. The scan is read-only — SELECTs only, no DDL, no DML — the analysis core makes no network calls, and nothing is uploaded to a service or a model provider. Your schema, your module text, your findings.
  • ●It says what it doesn't know. Uncertain inference reports Unknown. Dynamic SQL that can't be proven constant is counted with a machine-readable reason. An assistant acting on a confident wrong answer is worse than one told plainly what isn't known.
  • ●Or just gate CI. The same run emits SARIF, with each rule's helpUri pointing at its own page in the catalog — so the explanation travels with the finding.
Usage

One command, one pass, every rule.

SilentScan connects to a live database, reads its catalog from engine metadata instead of guessing from parsed DDL, and runs every readable view, procedure, function and trigger through all 234 rules in a single pass. 

silentscan scan-db <connection-string>                  # readable report
silentscan scan-db <connection-string> --format json    # for a tool or an assistant
silentscan scan-db <connection-string> --format sarif   # for CI
silentscan scan-corpus-live <manifest.json>             # many repositories at once

Types, per-column collations and the indexed flag are facts read from the engine, never guessed. Read-only by design: no DDL or DML is ever executed against the database you connect to.
