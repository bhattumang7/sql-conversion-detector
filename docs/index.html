Static analysis · SQL Server / T-SQL

Finds the bugs that only
show up in the query plan.

SilentScan connects to a real SQL Server database — a disposable dev copy, never assumed to be production — and reads its catalog straight from engine metadata instead of guessing from parsed DDL text. It resolves lineage through views and table-valued functions down to the base column, and confirms every plan claim against a real plan, never a guess from plan shape.

orders.OrderCode varchar(20) compared against a caller's value — same mismatch, opposite direction:
WHERE OrderCode = @code -- @code nvarchar(20) column converted · scan
WHERE OrderCode = CAST(@code AS varchar(20)) value converted · seek

T-SQL always converts the lower-precedence side. When that's the column, the index seek silently becomes a scan — no error, no warning, just a slower plan the next time someone looks. SilentScan only calls the first one a finding, and only after the plan XML shows CONVERT_IMPLICIT sitting on the column side of the predicate.

Most static analyzers stop at whichever layer they parse first — a raw SQL string, or one view's own column list. SilentScan doesn't stop there. A dynamic-SQL string proven constant at compile time is reparsed and handed back into the same lineage resolver static SQL uses — so a predicate buried inside EXEC(@sql), against a view built on another view, still traces to the real base column:

What it looks for

Implicit conversions and silent write loss
Direction- and collation-aware conversion detection — column-side vs. value-side, inherited through views and dynamic SQL — plus DML that truncates or rounds data with no engine error at all.
Sargability and index shape
Function-wrapped columns, leading-wildcard LIKE, column arithmetic, and composite-index predicates that constrain a trailing key column while leaving the leading one wide open.
Lineage-metric findings
The numbers that need the lineage pass to exist at all: real join width after every view and TVF expands, nested-view depth, and CTEs re-run once per reference instead of materialized once.
Plan-shape and correctness
MSTVFs used as row-count fences, scalar UDFs that block plan inlining, forced-serial constructs, and predicates that defeat cached-plan cardinality sniffing.
Dynamic SQL
Text that can be proven constant is analyzed exactly like static SQL, with findings remapped to their real source line — chained through nested views to a base column the same way static SQL is. Anything not provably constant is counted, never silently skipped.
Physical schema and index design
Unindexed foreign keys, duplicate and prefix-subsumed indexes, clustering-key quality, and identity ranges heading toward exhaustion — the catalog-only half of a DBA review.
Triggers, transactions, and cross-module correctness
Multi-row-unsafe triggers that collapse inserted/ deleted into one scalar, transactions with no guaranteed commit path, and write-ordering that only lineage can see across two separate procedures.
Code quality and maintainability
Structural metrics, dead code, duplication, naming, and deprecated syntax — the syntax-only rules, same finding schema as everything else above.

How it's verified

A conversion finding is confirmed only when the execution plan actually shows CONVERT_IMPLICIT on the column side of the predicate — never inferred from whether a small table happened to scan anyway. Every verdict-bearing rule defines its own equally specific plan marker and is checked against a live SQL Server instance, not a published compatibility matrix. Where inference is uncertain, the answer is Unknown, reported honestly, never guessed.

Rules also state their engine-version sensitivity — 2017 interleaved execution, 2019 UDF inlining, 2022 cardinality-estimator behavior — instead of assuming one SQL Server version's behavior is every version's.

Usage

silentscan scan-db <connection-string>        # read-only, SELECT-only
silentscan scan-corpus-live <manifest.json>

Output is versioned JSON, with a SARIF export for CI — each rule's helpUri links straight to its own page in the catalog.
