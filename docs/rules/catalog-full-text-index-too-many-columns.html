Full Text Index Too Many Columns

silentscan/catalog/full-text-index-too-many-columns

A medium-confidence or low-confidence finding of this same rule links here too - only the finding's certainty differs, not the underlying issue.

Why is this an issue?

A single CREATE FULLTEXT INDEX statement's column list carries more than 1,024 columns, the documented cap for a full-text index - reachable via wide-table sparse columns/column sets, which are not bound by the ordinary 1,024-column-per-table limit.

A single CREATE FULLTEXT INDEX statement's column list carries more than the documented 1,024-column limit for a full-text index. An ordinary table can never itself exceed 1,024 columns, but a wide table using sparse columns and a column set can carry far more, so the limit is reachable in practice even though it can never be hit by an ordinary table's column count alone. This is purely a count of the statement's own column list - no catalog or live connection needed.

How can I fix it?

Split the indexed columns across fewer, narrower full-text indexes (a table can carry only one full-text index, so this also means reducing which columns need full-text search at all), or drop columns from the list that don't actually need it.

A full-text index column list past the documented limit

Noncompliant code example

-- dbo.WideNotes is a wide table (WITH (DATA_COMPRESSION = ...) / column set)
-- carrying 1,100 sparse NVARCHAR columns.
CREATE FULLTEXT INDEX ON dbo.WideNotes(Col0001, Col0002, /* ... */ Col1100)
    KEY INDEX PK__WideNotes;

The column list carries more than 1,024 columns, over the documented full-text index limit.
