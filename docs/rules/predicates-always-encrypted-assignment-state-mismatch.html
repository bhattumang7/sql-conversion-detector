Always Encrypted Assignment State Mismatch

silentscan/predicates/always-encrypted-assignment-state-mismatch

A medium-confidence or low-confidence finding of this same rule links here too - only the finding's certainty differs, not the underlying issue.

Why is this an issue?

A column is assigned (via an UPDATE/MERGE SET clause) from another column whose Always Encrypted state differs - encrypted-vs-plaintext, or a different encryption type (deterministic vs. randomized) - oracle-confirmed (Msg 206: "Operand type clash ... is incompatible with ...") the statement never compiles regardless of which side is the source. Catalog-only structural fact - both columns' Always Encrypted status are DDL-time facts; only same-target-table-scope column-to-column assignments with statically resolvable base columns are checked.

Two Always Encrypted columns are only implicitly compatible when their encryption state matches exactly. Confirmed directly against a real SQL Server instance: assigning one column into another via an `UPDATE`/`MERGE` `SET` clause fails to compile with Msg 206 ("Operand type clash ... is incompatible with ...") whenever their encryption state differs - encrypted vs. plaintext (in either direction), or a different encryption type (deterministic vs. randomized), even when both columns share the same column encryption key.

Scoped to column-to-column assignments where both the target and the source resolve to a statically known base column (through the query's own scope, including joins and aliases) - an expression, function call, or parameter/variable source is never flagged, since the engine's own restriction (and the encrypted value's actual origin) is not staticaly decidable for those shapes.

How can I fix it?

Route the value through an Always Encrypted-enabled client - decrypt it and re-encrypt it to the target column's own key and algorithm - instead of assigning the encrypted value directly server-side.

Copying between differently-encrypted columns never compiles

Noncompliant code example

UPDATE dbo.Customer
SET SsnRandomized = SsnDeterministic;

SsnRandomized and SsnDeterministic use different encryption types - this UPDATE fails to compile with Msg 206 every time it runs, regardless of which column holds the source value.

Compliant solution

-- from an Always Encrypted-enabled client connection:
-- read SsnDeterministic (client decrypts it), then write it back
-- as a parameter (client re-encrypts it for SsnRandomized)
UPDATE dbo.Customer
SET SsnRandomized = @decryptedSsn;

The client decrypts the source value and re-encrypts it for the target column's own encryption type before the statement reaches the server.
