Unresolved Implicit Transaction

silentscan/control-flow/unresolved-implicit-transaction

A medium-confidence or low-confidence finding of this same rule links here too - only the finding's certainty differs, not the underlying issue.

Why is this an issue?

SET IMPLICIT_TRANSACTIONS ON is in effect (set earlier in the same module body) when an INSERT/UPDATE/DELETE/MERGE/TRUNCATE TABLE/a SELECT with a FROM clause/CREATE/ALTER TABLE/DROP/GRANT/REVOKE/OPEN CURSOR/FETCH CURSOR statement runs with no transaction already open - oracle-confirmed each of these silently starts a transaction exactly as if a BEGIN TRANSACTION had been written, with no BEGIN TRANSACTION anywhere in the source text. The same reachable-path analysis as the explicit BEGIN TRANSACTION rule then applies: a RETURN/THROW, or the natural end of the module body, reached with no intervening COMMIT/ROLLBACK leaves @@TRANCOUNT elevated by one. A bare SELECT with no FROM clause is oracle-confirmed to never start a transaction under this setting.

`SET IMPLICIT_TRANSACTIONS ON` changes what opens a transaction - once it's on, the next `INSERT`/`UPDATE`/`DELETE`/`MERGE`/`TRUNCATE TABLE`, a `SELECT` with a `FROM` clause, a `CREATE`/`ALTER TABLE`/`DROP`, a `GRANT`/`REVOKE`, or an `OPEN`/`FETCH` against a cursor silently starts a transaction with no `BEGIN TRANSACTION` anywhere in the source text. This is oracle-confirmed directly: each of those statement kinds bumps `@@TRANCOUNT` from 0 to 1 under this setting with no explicit `BEGIN TRANSACTION` at all, and a bare `SELECT` with no `FROM` clause is oracle-confirmed to never do this.

The same reachable-path analysis this tool already applies to an explicit `BEGIN TRANSACTION` applies here too: a `RETURN`/`THROW`, or the natural end of the module body, reached with no intervening `COMMIT`/`ROLLBACK` after one of these statements ran leaves `@@TRANCOUNT` elevated by one, holding locks exactly as an unresolved explicit transaction would - except there's no `BEGIN TRANSACTION` in the code to draw the eye to it.

How can I fix it?

Ensure every RETURN/THROW path, and the natural end of the module body, is preceded by a matching COMMIT or ROLLBACK once SET IMPLICIT_TRANSACTIONS ON is in effect - or turn the setting back off if leaving a transaction implicitly open wasn't intended.

An implicitly opened transaction that is never closed

Noncompliant code example

CREATE PROCEDURE dbo.usp_ProcessOrder
    @OrderId INT
AS
BEGIN
    SET IMPLICIT_TRANSACTIONS ON;
    UPDATE dbo.Orders SET Status = 'Processing' WHERE Id = @OrderId;
    SELECT @OrderId;
END;

SET IMPLICIT_TRANSACTIONS ON turns the UPDATE into the start of a transaction with no BEGIN TRANSACTION written anywhere - the procedure body ends with no COMMIT or ROLLBACK, leaving @@TRANCOUNT elevated by one for the calling session.

Compliant solution

CREATE PROCEDURE dbo.usp_ProcessOrder
    @OrderId INT
AS
BEGIN
    SET IMPLICIT_TRANSACTIONS ON;
    UPDATE dbo.Orders SET Status = 'Processing' WHERE Id = @OrderId;
    COMMIT TRANSACTION;
    SELECT @OrderId;
END;

The implicitly opened transaction is committed before the procedure returns on every path, so no locks are left held.
