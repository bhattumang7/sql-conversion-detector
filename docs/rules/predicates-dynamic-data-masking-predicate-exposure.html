Dynamic Data Masking Predicate Exposure

silentscan/predicates/dynamic-data-masking-predicate-exposure

A medium-confidence or low-confidence finding of this same rule links here too - only the finding's certainty differs, not the underlying issue.

Why is this an issue?

A Dynamic Data Masking column is used as a direct operand of a comparison, BETWEEN, LIKE, IN, GROUP BY, or ORDER BY - oracle-confirmed the engine evaluates these against the real underlying value regardless of the caller's UNMASK permission, so a caller who never sees the real value in output can still infer it (equality/range probing, or directly through GROUP BY's distinct-group count or ORDER BY's relative row order) - masking protects displayed output only, never predicate/sort/group evaluation.

Dynamic Data Masking (`MASKED WITH (FUNCTION = ...)`) rewrites a masked column's displayed value for any caller who lacks the `UNMASK` permission - a `default()`-masked `INT` shows `0`, a masked `DATETIME` shows `1900-01-01`, `email()` shows an obfuscated address, and so on. That substitution happens only when the column's value is returned as output. It has no effect on how the engine evaluates a predicate, an `ORDER BY` key, or a `GROUP BY` key: those always compare the real, unmasked stored value, oracle-confirmed directly against the engine - `WHERE MaskedColumn = @guess` matches or fails to match based on the real value even though the same query's `SELECT MaskedColumn` would have displayed the sentinel, and `GROUP BY MaskedColumn` produces one group per distinct real value even though every group's displayed key looks identical.

This turns masking into a boolean- or ranking-oracle: a caller with no `UNMASK` grant can still recover the real value of a masked column by probing it in a `WHERE`/`JOIN ON`/ `HAVING` predicate and observing which rows come back, by counting `GROUP BY` groups, or by reading relative row order from `ORDER BY` - all without ever seeing the real value in an output column. Nothing about the query's shape looks unusual, and nothing errors.

How can I fix it?

Do not filter, join, group, or sort on a masked column for principals that must not see its real value - move the check behind a view or computed flag that does not itself leak the real value, or grant UNMASK only to principals who are already trusted with the real data.

A WHERE-clause equality check silently exposes the real value

Noncompliant code example

CREATE TABLE dbo.Customers
(
    CustomerId INT NOT NULL PRIMARY KEY,
    Ssn        VARCHAR(11) MASKED WITH (FUNCTION = 'default()') NOT NULL
);

SELECT CustomerId FROM dbo.Customers WHERE Ssn = @candidateSsn;

A caller without UNMASK sees only the default() sentinel from any SELECT Ssn, but this predicate is evaluated against the real stored value - repeating the query with different @candidateSsn values lets that caller recover the real SSN one guess at a time, entirely through which rows come back.

Compliant solution

CREATE TABLE dbo.Customers
(
    CustomerId INT NOT NULL PRIMARY KEY,
    Ssn        VARCHAR(11) MASKED WITH (FUNCTION = 'default()') NOT NULL
);

SELECT CustomerId FROM dbo.Customers WHERE CustomerId = @customerId;

The predicate no longer touches the masked column at all, so a caller without UNMASK cannot use this query to probe the real Ssn value.
