String Split Separator Length

silentscan/string-tvf/string-split-separator-length

A medium-confidence or low-confidence finding of this same rule links here too - only the finding's certainty differs, not the underlying issue.

Why is this an issue?

STRING_SPLIT's separator argument is a literal (or constant-folded, or a literal NULL) whose length is not exactly one character - oracle-confirmed (Msg 214: "Procedure expects parameter 'separator' of type 'nchar(1)/nvarchar(1)'") the call fails at compile/bind time, before any row is read; pure source-level constant-folding, no catalog dependency.

STRING_SPLIT's separator parameter is declared as nchar(1)/nvarchar(1) - the engine only ever accepts exactly one character. This was probed directly against a real engine: a separator argument whose length is not exactly one - whether zero characters, two or more characters, a literal NULL, or an expression that constant-folds to any of those - raises Msg 214 ("Procedure expects parameter 'separator' of type 'nchar(1)/nvarchar(1)'") at compile/bind time, before a single row is read. Unlike a runtime data-dependent failure, this call never succeeds regardless of what the first argument's own value is.

This is pure source-level constant-folding with no catalog dependency - a bare string literal, a literal NULL, or a constant string concatenation are all resolved the same way, without needing to know anything about the surrounding schema.

How can I fix it?

Change the separator argument to a single character - STRING_SPLIT accepts exactly one character and nothing else.

STRING_SPLIT with a two-character separator literal

Noncompliant code example

SELECT value FROM STRING_SPLIT('a,,b', ',,');

The separator argument ',,' is two characters long - the call raises Msg 214 before any row is read.

Compliant solution

SELECT value FROM STRING_SPLIT('a,,b', ',');

A single-character separator is valid - STRING_SPLIT accepts exactly one character.
