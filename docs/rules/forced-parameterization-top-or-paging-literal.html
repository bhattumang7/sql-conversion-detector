TOP Or Paging Literal

silentscan/forced-parameterization/top-or-paging-literal

A medium-confidence or low-confidence finding of this same rule links here too - only the finding's certainty differs, not the underlying issue.

Why is this an issue?

A TOP row count or OFFSET/FETCH paging count is a literal - the engine leaves it unparameterized even under PARAMETERIZATION FORCED, so a workload varying the page size still recompiles per distinct value.

Reported only when the target database has `PARAMETERIZATION FORCED` on. Confirmed directly against a real engine: a literal `TOP N`, and a literal `OFFSET n ROWS FETCH NEXT m ROWS ONLY`, both stay untouched in the cached plan while an unrelated equality predicate in the same statement correctly parameterizes.

A paginated query - one of the most common shapes in real application code - varying only its page size or offset gets a fresh compile per distinct value, right where PARAMETERIZATION FORCED was expected to collapse them into one shared plan.

How can I fix it?

Pass the row count as a parameter or local variable (`TOP (@N)`, `OFFSET @Skip ROWS FETCH NEXT @Take ROWS ONLY`) instead of a literal.

A literal page size

Noncompliant code example

SELECT OrderId FROM dbo.Orders ORDER BY OrderId OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY;

Under PARAMETERIZATION FORCED, 20 and 10 both stay literal in the cached plan - a different page size recompiles instead of reusing this plan.

Compliant solution

CREATE PROCEDURE dbo.GetOrdersPage @Skip int, @Take int AS
SELECT OrderId FROM dbo.Orders ORDER BY OrderId OFFSET @Skip ROWS FETCH NEXT @Take ROWS ONLY;

The paging counts are already parameters, so every call shares the one compiled plan regardless of PARAMETERIZATION FORCED.
